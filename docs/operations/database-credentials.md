# DBの認証情報

`docker-compose-dev.yml` のDB初期化用設定は、Git管理外の `db.env` から読む。
別の場所に置く場合はCompose用 `.env` の `POSTGRES_ENV_FILE` で指定する。

開発環境では `db.env.example` を `db.env` にコピーし、DB名・ユーザー・パスワードを設定して権限を0600にする。
Djangoの接続情報は従来どおり `secret.env` の `DB_NAME` / `DB_USER` / `DB_PASS` で設定する。
既存DBを使う場合はそのDBの有効な認証情報に合わせる。値を表示する `docker compose config` は使用しない。

本番では、DB管理用とアプリ用のユーザー・パスワードを分ける。
管理用のenvファイルはアプリのbind mount対象ディレクトリ外へ置き、所有者のみ読めるようにする。
アプリ用ロールにはsuperuser、createdb、createrole、replication、bypassrlsを与えない。
既存のアプリ所有テーブルと必要なスキーマ権限は保持する。
PostgreSQLの初期管理者はsuperuser属性を外せないため、初期管理者をアプリ接続に使っていた場合は
通常権限の別ロールを作り、アプリDB・アプリのスキーマ内オブジェクトの所有権を移して接続先を切り替える。
システムカタログや他DBまで対象になる一括の所有権移譲は行わない。

既存PostgreSQLボリュームのパスワードはenvファイルを書き換えるだけでは変わらない。
変更前にバックアップを検証し、DBロールのパスワードとアプリ設定を一緒に変更して、
環境変数を読み直すためアプリ・cronコンテナを再作成する。DBボリュームは削除しない。
旧パスワードでの接続拒否、新しいアプリ接続、管理用接続、権限・データ保持を確認する。

新しいDBへの復元時は、まず管理用ロールでDBを初期化し、別のアプリ用ロールを作成してから
データを復元する。管理用の認証情報をアプリへ渡して起動する方法は使わない。

秘密値はGit・標準出力・SQLコマンドライン引数へ載せない。具体的なパス・復旧用設定は非公開の運用記録で管理する。
Dockerビルドは `.dockerignore` で秘密設定と作業・データ領域を除外する。
CIのGitleaks検査は無効化済みの旧履歴の特定箇所だけを例外にし、新しいコミットへの同じ値の再混入も拒否する。
テスト用DBの例外はCIファイルと使い捨ての固定値の組み合わせだけに限定する。
