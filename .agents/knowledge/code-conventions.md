# コーディング規約

## Python / Django

機能ごとに、責務でファイルを分ける既存構成を維持する。

| ファイル | 責務 |
|---|---|
| `models.py` | データモデル |
| `forms.py` | 入力検証 |
| `views.py` | HTTP 処理 |
| `services.py` | **更新を伴う**業務処理 |
| `selectors.py` | **データ取得**処理 |

- Python コードには可能な限り型注釈を付ける
- 設定は `project/settings/` の適切な環境別ファイルに記述する
- モデル変更時は新しい migration を作成する。**過去の migration は原則編集しない**
- 日時処理では `USE_TZ = True` と `Asia/Tokyo` を考慮する

## TypeScript

- フロントエンドの処理は `src/ts/*.ts` に実装する
- **`static/app/*.js` を直接編集しない**（コンパイル出力。変更後は `npm run build`）
- `var` を使わず `const` / `let` を使う
- `any` を避け、`unknown` から適切に型を絞り込む
- 関数の引数と戻り値に型注釈を付ける
- 可能な限り Vanilla JavaScript を使い、jQuery への依存を増やさない

## 互換性として扱うもの

URL名、フォームフィールド名、テンプレート変数、API形式は互換性の一部。
安易に変更しない。

## UI刷新の判断（2026-09-07）

- ユーザーの優先事項はシンプルさ、スマホでの操作性、速度。装飾より情報の優先順位を重視する。
- 2026-09-09、刷新後の文字を「もう少しだけ大きく、または太く」と希望。軽さだけを優先せず、控えめに大きめ・操作ラベルはやや太めにする。全面的な太字化は避ける。
- 共通の方向性は淡いニュートラル背景、白い面、藍の主操作、細い境界線。既存の暗いトップバーは維持する。
- デザイン刷新だけを理由にSPA化やBootstrapの全面移行を同時実施しない。既存のフォーム、モーダル、デモの互換性を段階的に検証するため。
- 操作全体の現代化については、ユーザーがまず1画面の試作を選択（2026-09-09）。メモ画面で操作感を確認してから共通化する。試作とBootstrap移行を同時に行わず、見た目/操作の評価と互換性リスクを分離する。
- メモ試作へのフィードバック: 一律に大きいボタンは好まれない。コンパクトな操作部品と周囲の余白で情報を整理し、主操作・補助操作・アイコン操作の見た目を役割ごとに統一する。文字を大きめにする希望と、ボタン全体の大型化は区別する。
- この方針はメモだけでなく他画面にも適用することをユーザーが承認済み。画面別に独自のボタン寸法を増やさず、本文の共通寸法を使う。ヘッダー・下部ナビや密度の高いカレンダーは用途を優先する。
- ユーザーは主要画面だけでなく認証・アカウント・問い合わせ・管理・案内まで全画面の統一を希望。共通CSSの配信だけで完了とせず、独自フォーム・タブ・装飾も確認する。Django管理の既存操作・暗色モードは維持し、オフライン案内は外部資産に依存させない。
- ページ固有CSSもheadのextra_cssブロックで読み込む。本文での後読みは初期描画のちらつきと優先順位の混乱につながる。
- 再評価では色・角丸だけの全体上書きを完成と扱わない。一覧・入力・カレンダーの幅を用途で明示し、Bootstrapの汎用containerを拡幅して認証フォームまで巻き込まない。
- 色は操作とユーザーデータを区別する。操作の選択状態は藍へ統一するが、ユーザーが設定したカテゴリ・予定ラベルの色は勝手に変更しない。
- 速度改善は非表示グラフの生成数や配信バイト数を測る。ファイルの圧縮率をページ表示時間の改善率と読み替えない。
- ユーザーは残フェーズについてメモ通りの実装を必須にしていない。迷い・待ち・操作負担を減らすことを優先し、根拠があれば順序と手段を変えてよい。
- 認証済みページのオフライン保存は行わない。複数アカウントの情報混在・古い記録の表示を避けるため、速度改善は資産のHTTPキャッシュと不要描画削減で行う。
- スワイプやcanvasクリックだけに操作を依存させない。ボタンでも同じ処理に到達できるようにし、二重実装による挙動差を避ける。
