# 本番環境の不正アクセス・不正プログラム調査

調査日時: 2026-10-22 12:21〜12:27 JST。対象: CarbohydrateProのLightsail本番インスタンスと対応するCloudFront。

追記: 調査後、SSH・8000番の接続元制限とNginx 1.30.6への更新を実施した。以下は調査時点の記録。現在の対策状況は [対策実施報告](production-security-hardening-2026-10-22.md) を参照。

## 結論

攻撃・探索の試行は確認した。調べた範囲では、侵入成功、不正プログラムの稼働、不審な永続化を示す証拠は見つからなかった。
ただし、OSとNginxの更新状況、公開ポート、利用者の接続元を追跡できないログ設定には対策が必要。
これは稼働状態と保存済みログによる点検であり、未侵害を保証するものではない。

## 調査範囲と結果

### SSH・OSアカウント

- `/var/log/secure` とローテーション4ファイルを集計。保持期間は2026-09-20〜10-22。
- `Invalid user` は2,725記録。自動的なユーザー名探索がある。これは接続数・攻撃者数とは異なる。
- 調査開始前のログイン成功は22件。すべて `ec2-user` の公開鍵認証で、今回の調査と同じ接続元・同じ鍵指紋だった。鍵指紋はローカルの本番用SSH鍵とも一致。
- 対象期間内のrootログイン成功、OSユーザー追加・変更イベントは検出しなかった。
- パスワード認証と対話式認証は無効。`PermitRootLogin yes` だが、rootの登録鍵にはec2-userへのログインを促す強制コマンドが付いている。登録鍵はroot/ec2-user各1本で、更新日時は2024年6月。
- 過去の `wtmp` には別の接続元もあるが、対応する古い認証ログを今回すべて照合したわけではない。

### Web・アプリの認証

- 現在のNginxコンテナログ: 2026-10-13 16:11〜10-22 03:03 UTC。解析できたHTTP要求は6,448件、うち404は5,061件。
- `.env`、`.git/config`、WordPress/PHP等の探索パターンに該当する404は4,150件。代表例は `/.env` 29件、`/.git/config` 13件、`/xmlrpc.php` 27件。
- 同パターンの200応答3件は、正常な静的ファイル `/static/app/vendor/chart...js` が `vendor` に一致したもの。機密ファイル取得成功を示す200は検出しなかった。
- `/system-control-panel/.env` は1件302。内容取得成功とは判断できない。ほかに探索パターンの499が5件あるため、「すべて404だった」とは言えない。

### 稼働プロセス・通信・永続化・ファイル

- nginx、gunicorn、cron、PostgreSQLの4コンテナが稼働。特権コンテナはなく、Dockerソケットのマウントも確認しなかった。
- プロセスの実行ファイルと所属を確認。採掘プログラム、テンポラリ領域からの実行、削除済み実行ファイル、不審な常駐処理は検出しなかった。`unpigz` はDockerサービス配下のプロセスだった。
- 確認時のホストの確立済みTCP接続は調査用SSH。各コンテナのネットワーク名前空間では確立済みTCP/UDP通信は検出しなかった。これは一時点の状態であり、過去や間欠的な通信は網羅しない。
- コンテナCPU使用率は0.00〜0.01%。ホストの負荷平均は0.00、連続稼働約655日。
- systemdサービス・タイマー、cron、atキュー、rc.local、LD_PRELOAD設定を確認。不審な自動起動設定は検出しなかった。
- 独自cronは既存リポジトリのDocker整理・ログ保管処理と対応。コンテナcronは定期支払い・日次セキュリティ集約・カレンダー同期だった。調査ではこれらを手動実行していない。
- `/tmp`、`/var/tmp`、`/dev/shm` の検査対象に実行可能ファイルなし。media領域にも実行権限付きファイルや検査対象のスクリプト拡張子はなかった。全ファイルの内容検査ではない。

- 本番リポジトリの追跡対象ファイルに未コミット差分なし。未追跡は `static/.gitkeep` のみ。HEADは `8b294bd`。nginx/gunicornのコンテナ差分も確認し、表示された差分はキャッシュ・実行時ディレクトリ等だった。
- ログアーカイブの進捗は10月22日03:00 UTCまで。直近300行にアーカイブ失敗はなく、最終記録は03:10 UTC。S3に保存された全過去ログの取得・再解析は実施していない。

## 優先して対策する点

1. **OS・Nginxの更新。** 実機はAmazon Linux 2、稼働カーネルは `4.14.344-262.563.amzn2.x86_64`（導入記録2024-05-29）。AL2は2026-06-30にEOLを迎えたと[AWS公式リリースノート](https://docs.aws.amazon.com/AL2/latest/relnotes/relnotes-20260825.html)に記載されている。Nginxの実バージョンは1.17.7で、[公式セキュリティ情報](https://nginx.org/en/security_advisories.html)の複数の影響バージョン範囲に含まれる。個別の脆弱性の成立条件・悪用の有無は今回確定していない。Gunicornはイメージ名が20.1.0でも、実バージョンは26.2.0だった。
2. **SSHとオリジンの公開範囲を制限。** LightsailではTCP 22/80/443/587/8000がIPv4・IPv6とも全世界に許可されている。実際の待ち受けは主に22/8000で、80/443/587には今回待ち受けを確認していない。8000はCloudFront以外からも到達可能な設定であり、信頼する入口を限定する対策が必要。111等のホスト待ち受けは確認したが、Lightsailの公開許可には含まれていない。
3. **本来のクライアントIPを安全に記録。** CloudFront→Nginx→Djangoの信頼境界を定義してから修正する。任意の `X-Forwarded-For` 先頭値を無条件に信頼する変更は避ける。CloudFront設定の `Logging.Enabled` はfalse、WebACL関連付けは空。別方式のログ配信設定までは検査していない。オリジン接続はHTTP、カスタムヘッダー設定はなかった。

今回の調査では、本番の設定変更、更新、再起動、プロセス停止、能動的な攻撃テストは行っていない。SSH・sudo等による通常の調査アクセスログは残る。
全ディスク・メモリのフォレンジック、過去の全S3ログ、CloudTrailによるAWSアカウント操作履歴、全依存パッケージの脆弱性検査は対象外。
